v0.9.4: storage.clear command — the missing half of logout (live-verified)

User-reported symptom: after login, Notion redirects to the last-used page
of the PREVIOUS account. Root cause (measured live in the user's browser):
cookies.remove cleared 16/16 cookies fine, but 122 localStorage keys
survived — including lastVisitedRoute, current-user-id (old account),
sidebar state, BlockFrecency keyed by old user ids. Plus sessionStorage
(5), IndexedDB (3 DBs — Notion's TransactionStore can hold queued offline
transactions from a previous session), and 2 service-worker caches.

- NEW storage.clear command: wipes localStorage + sessionStorage +
  IndexedDB + Cache API for an origin. Closes other same-origin tabs first
  (releases IDB handles, stops in-memory state being written back), opens
  a temp tab on the origin when none exists. All storage surfaces
  individually toggleable.
- cookies.remove hardened: sweeps the whole registrable domain (not just
  the url's subdomain — host-only cookies on www.notion.com were missed)
  and removes per (name, domain, path) so same-name duplicates across
  domain variants each die.
- All four signup macros (signup, signup-rest, full-onboarding, self-test)
  now run cookies.remove → storage.clear before opening the page.
- todoist reference finding: its flow needs no clearing because it uses a
  fresh requests.Session() per signup — clean by construction. The
  extension inherits the user's browser state, so clearing must be
  explicit. Lesson recorded in SKILL.md §1.17.
- Updated SKILL-consumer.md to the user's improved revision + live
  findings addendum: chained mail is stored under the APEX address form
  (admin@priv.email), not the v3-mail form the doc claims — query both
  until the coming query-API unifies them.
- Dry-run harness: storage.clear mocked; 9/9 macros, 128/128 steps PASS.

Live verification performed in the user's browser: closed other notion
tabs, ran the clear — localStorage 122→0, lastVisitedRoute gone, all 3
IndexedDB deleted, both caches deleted.
